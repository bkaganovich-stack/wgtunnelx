# WG Tunnel X — план разработки

Документ описывает, что и почему сделано в форке, как он устроен, где его слабые места и что делать дальше. Состояние на октябрь 2026, база — WG Tunnel 5.8.2, Xray-core 26.10.21.

## 1. Цель и рамки

**Цель.** Дать WG Tunnel раздельную маршрутизацию по доменам с той же гибкостью, что у Xray и клиентов на его основе (v2rayNG, v2RayTun): правила по `geosite`/`geoip`, доменам, IP, портам, протоколам и приложениям; решение для каждого соединения, без таблицы маршрутов Android.

**Обязательные условия.**

1. Все возможности WG Tunnel сохраняются, включая AmneziaWG.
2. Форк должен сам выпускать новую версию сразу после стабильного релиза WG Tunnel. Значит, изменения в файлах апстрима должны быть минимальными и предсказуемыми, иначе каждое слияние будет требовать человека.
3. Название — WG Tunnel X, репозиторий `wgtunnelx`, иконка — стилизованная X в графике оригинальной W.

**Вне рамок первой версии:** собственные Xray-протоколы (VLESS, Reality и т. п.) как выходы, балансировщики, маршрутизация в режимах «Локальный прокси» и «Lockdown».

## 2. Выбранная архитектура

### 2.1. Варианты, которые рассматривались

| Вариант | Плюсы | Почему отклонён / принят |
| --- | --- | --- |
| A. Встроенный WireGuard-outbound Xray | Один движок | Нет AmneziaWG, теряются восстановление, DNS-бутстрап и статистика WG Tunnel. **Отклонён** |
| B. Форк `wgtunnel/core` (Go-бэкенд) с маршрутизацией внутри | Один процесс, один TUN | Второй форк с тяжёлой сборкой Go/NDK, конфликты при каждом обновлении ядра. **Отклонён** |
| C. sing-box вместо Xray | Встроенный WireGuard, rule-set | Требование — поведение и базы Xray; AmneziaWG в sing-box нет. **Отклонён** |
| D. Бэкенд WG Tunnel в userspace-режиме + Xray-core, который владеет VPN | Бэкенд не трогаем, AmneziaWG работает, правила 1:1 как в Xray | **Принят** |

### 2.2. Поток трафика (вариант D)

```
Приложения ─► TUN (XrayVpnService) ─► Xray-core (inbound tun, sniffing http/tls/quic)
                                          │  routing: правила пользователя
                                          ├─ proxy  ─► SOCKS5 127.0.0.1:<случайный порт>, логин/пароль случайные
                                          │             └─► бэкенд WG Tunnel в Proxy-режиме (AmneziaWG + gVisor netstack) ─► сервер
                                          ├─ direct ─► сокеты приложения; приложение исключено из собственного VPN,
                                          │             поэтому трафик уходит в обычную сеть без петель
                                          ├─ block  ─► blackhole
                                          └─ dns-out ─► DNS-модуль Xray: «туннельные» домены через DNS туннеля,
                                                       «прямые» — через системный резолвер
```

Ключевые решения:

- **TUN читает сам Xray.** В Xray-core есть inbound `tun`, на Android он получает дескриптор через `xray.tun.fd` ([proxy/tun](https://github.com/XTLS/Xray-core/tree/main/proxy/tun)). Библиотека [AndroidLibXrayLite](https://github.com/2dust/AndroidLibXrayLite) передаёт его в `CoreController.startLoop(config, tunFd)`. Промежуточный tun2socks не нужен.
- **Xray работает в отдельном процессе `:xray`.** AmneziaWG (`libam-go.so`) и Xray (`libgojni.so`) написаны на Go, и у каждой библиотеки свой рантайм Go. Два рантайма в одном процессе делят обработчики сигналов: сбой в коде одного рантайм принимает за свой другой, после чего Xray падает с `fatal error: unknown caller pc`, а процесс зависает с поднятым VPN без трафика. Такое произошло в версии `5.8.2-x.1` на телефоне пользователя. Разработчики Go такую конфигурацию не поддерживают ([golang/go#22192](https://golang.org/issue/22192), [golang/go#18976](https://golang.org/issue/18976)). Поэтому `XrayVpnService` объявлен с `android:process=":xray"`, а приложение управляет им через `Messenger` (`XrayEngine` ↔ `XrayVpnService`, протокол в `XrayIpc`). Если процесс Xray умирает, приложение останавливает туннель, а автотуннель при необходимости поднимает его заново. Если умирает процесс приложения, `:xray` сам закрывает VPN. Если Xray не подтверждает остановку за 5 секунд, его процесс завершается принудительно, и остановка всё равно срабатывает.
- **Собственное приложение исключено из VPN** (`addDisallowedApplication`). UDP-сокет WireGuard и `direct`-сокеты Xray идут в физическую сеть без `protect()`, петли маршрутизации невозможны.
- **Бэкенд WG Tunnel не изменён.** Режим `BackendMode.Proxy.Standard` уже есть в апстриме (он же используется для «Локального прокси»), SOCKS5 в нём поддерживает UDP ASSOCIATE (go-socks5 в [wireproxy-awg](https://github.com/wgtunnel/wireproxy-awg)).
- **Подмена через DI.** `RoutingTunnelProvider` — декоратор `TunnelProvider`, объявленный в Koin-модуле форка, который грузится после модулей апстрима и перекрывает исходное определение. Он перехватывает только запуск в режиме VPN для туннелей, к которым применяется маршрутизация. Остальные вызовы уходят в апстрим без изменений.
- **Настройки отдельно от Room.** Схема БД и номера миграций принадлежат апстриму; собственная миграция форка конфликтовала бы с каждой будущей. Правила лежат в `files/xray/routing.json`.
- **Гео-базы не в APK.** Файл geosite runetfreedom весит ~74 МБ. Базы скачиваются при включении, проверяются (парсинг списка категорий) и заменяются атомарно. Xray читает их потоково, поэтому размер файла почти не влияет на память.

### 2.4. Точки врезки в апстрим

Все изменения файлов WG Tunnel перечислены в `scripts/apply-hooks.py` — их шесть, около 20 строк:

1. `app/build.gradle.kts` — `apply(from = "wgtunnelx.gradle")` в конце файла;
2. `settings.gradle.kts` — `include(":xray")`;
3. `WireGuardAutoTunnel.kt` — `xrayModule` в списке модулей Koin и ранний выход из `onCreate`/`onTrimMemory` в процессе `:xray` (там не должны запускаться Koin, бэкенд и AmneziaWG);
4. `di/NetworkModule.kt` — проверка обновлений в репозитории форка;
5. `SettingsScreen.kt` — строка «Маршрутизация по доменам (Xray)»;
6. `logcatter/.../LogcatStreamReader.kt` — без фильтра `--pid`, чтобы в экспорт журнала попадали записи процесса `:xray` и предыдущих процессов (logd и так отдаёт приложению только его собственные записи).

Хуки идемпотентны. Если при слиянии в одном из этих файлов конфликт, берётся версия апстрима и хуки накладываются заново по якорям.

## 3. Автоматический выпуск

| Workflow | Когда | Что делает |
| --- | --- | --- |
| `x-upstream-release` | cron каждые 15 мин + вручную | Берёт `releases/latest` у `wgtunnel/android` (этот эндпоинт не возвращает черновики и пре-релизы), проверяет формат `X.Y.Z` и наличие релиза форка. Сливает тег, разрешает конфликты по политике, собирает, тестирует, публикует `X.Y.Z-x.1` |
| `x-release` | вручную | Релиз изменений форка без нового апстрима: `xRevision + 1` |
| `x-update-xray` | раз в неделю | Обновляет `libv2ray.aar` до свежего релиза, коммитит только если тесты и проверка конфигов прошли |
| `x-ci` | push / PR | Хуки на месте, юнит-тесты, проверка конфигов реальным Xray, debug-сборка |

**Политика конфликтов** (`scripts/resolve-upstream-conflicts.sh`):

- `.github/**` апстрима — удаляется (воркфлоу апстрима в форке не нужны и не должны запускаться; новые воркфлоу апстрима тоже вычищаются);
- `README.md` — остаётся версия форка (`.gitattributes`, драйвер `ours`);
- файлы с хуками — версия апстрима + повторное наложение хуков;
- всё остальное — слияние откатывается, создаётся issue со списком файлов и командами для ручного слияния.

Механизм проверен локально на синтетических релизах: изменённый и новый воркфлоу апстрима, изменения рядом с хуком, прямой конфликт в строке хука. Во всех случаях релиз собирался без участия человека; невосстановимый конфликт корректно откатывается с кодом 2.

**Что нужно знать про GitHub Actions:**

- Задержка. Минимальный интервал расписания — 5 минут, при нагрузке запуски сдвигаются, поэтому реальная задержка обычно 15–30 минут после релиза апстрима. Мгновенно реагировать на чужой репозиторий без его вебхуков нельзя.
- 60 дней. В публичных репозиториях расписания отключаются после 60 дней без активности ([документация GitHub](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows)). Активность создают слияния апстрима и еженедельное обновление Xray; дополнительно workflow раз в сутки вызывает API `enable` для своих расписаний.
- Форк через кнопку Fork. В форках публичных репозиториев расписания по умолчанию выключены (та же страница документации), поэтому `wgtunnelx` создаётся как обычный репозиторий.
- Права на воркфлоу. Если коммиты апстрима меняют `.github/workflows`, `GITHUB_TOKEN` не сможет их запушить; нужен токен с правом `workflows` (секрет `SYNC_TOKEN`, см. [RELEASING.md](RELEASING.md)).

## 4. Проверка качества

Что сделано и проверено при создании форка:

- юнит-тесты модуля `:xray` (17 тестов): порядок правил, DNS, fake DNS, правила по приложениям, пользовательский конфиг, валидатор, импорт/экспорт, чтение гео-баз;
- **все пресеты и конфиг со всеми типами условий проходят `xray run -test` на Xray-core 26.10.21 с реальными базами runetfreedom** — это та же проверка, что выполняется в CI перед каждым релизом (`scripts/validate-xray-configs.sh`);
- категории пресетов сверены со списком кодов в geosite/geoip runetfreedom;
- сборка `assembleStandaloneDebug` и подписанная `assembleStandaloneRelease` с R8: классы gomobile сохраняются, манифест содержит сервис и Activity форка, applicationId `com.wgtunnelx.android`, authority `wgtunnelx.provider` (не конфликтует с оригиналом), гео-файлов в APK нет.

**Чего ещё не было:** запуска на реальном устройстве. Перед первым публичным релизом нужен ручной прогон (раздел 6, этап 1).

## 5. Известные ограничения

1. Маршрутизация работает в режиме **VPN**. В режимах «Локальный прокси» и «Lockdown» туннель запускается как в апстриме.
2. На карточке туннеля и в уведомлении маршрутизируемый туннель показан как прокси с внутренним адресом `127.0.0.1:порт`. Исправление требует правок UI апстрима, отложено.
3. `AllowedIPs` туннеля ограничивают то, что может пройти через `proxy`. Для маршрутизации нужен `0.0.0.0/0, ::/0`; частные сети из `AllowedIPs` автоматически закрепляются за туннелем раньше правила «локальная сеть напрямую».
4. Правила по приложениям требуют Android 10+ (`ConnectivityManager.getConnectionOwnerUid`).
5. Размер APK: ядро Xray добавляет около 33 МБ нативного кода на архитектуру.
6. Экран маршрутизации — отдельная Activity, PIN-блокировка приложения на него не распространяется (правила не содержат секретов).

## 6. Дорожная карта

**Этап 1 — первый релиз (1–2 недели).**
- Создать репозиторий, секреты, первый релиз `5.8.2-x.1` через `x-release`.
- Ручное тестирование на 3–4 устройствах (Android 8, 10, 13, 15/16): запуск/остановка, переключение Wi-Fi ↔ мобильная сеть, always-on VPN, автотуннель, AmneziaWG-конфиг, обновление гео-баз, IPv6-сеть, правила по приложениям.
- Замер расхода батареи и памяти с базой runetfreedom.

**Этап 2 — удобство (2–4 недели).**
- Статус «Xray routing» на карточке туннеля и в уведомлении вместо «прокси».
- Тест правила: ввод домена → какое правило сработает (через `routing` API Xray).
- Профили правил и выбор профиля для каждого туннеля.
- Бэкап правил вместе с бэкапом WG Tunnel.

**Этап 3 — расширения.**
- Маршрутизация поверх режима Lockdown.
- Несколько туннелей как разные outbound'ы (например, `geosite:youtube` → туннель A, `geosite:openai` → туннель B).
- Дополнительные outbound'ы Xray (VLESS/Reality) как отдельные цели правил.

### Автотуннель в форке

`AutoTunnelWatchdog` дополняет автотуннель апстрима, не меняя его логику:

- если автотуннель включён в настройках, но его служба не работает (процесс остановили принудительно, его убил менеджер задач производителя, приложение упало), служба запускается снова, как только приложение выходит на передний план;
- в релизных сборках журнал апстрима не содержит решений автотуннеля (отладочные записи отбрасываются). Форк пишет на уровне INFO состояние службы, сеть, которую она видит (тип, первая буква SSID, `usable`, состояние VPN), и каждый запуск/остановку туннеля с источником (`USER` или `AUTO_TUNNEL`).

## 7. Риски и как они закрыты

| Риск | Мера |
| --- | --- |
| Апстрим переписал код рядом с хуками | Хуки накладываются по якорям; если якорь пропал — issue и ручное слияние |
| Апстрим изменил API `TunnelProvider` / бэкенда | CI-сборка падает до публикации, создаётся issue, старый релиз остаётся актуальным |
| Новая версия Xray меняет схему конфига | Еженедельное обновление проходит `xray run -test` на всех пресетах до коммита |
| Категории исчезли из гео-баз | Валидатор перед запуском туннеля + понятная ошибка в UI |
| Компрометация `libv2ray.aar` | Версия закреплена, поддерживается проверка SHA-256 (`xray/libxray.sha256`), можно собрать AAR из исходников |
| Два рантайма Go в одном процессе | Xray вынесен в процесс `:xray`; гибель процесса обрабатывается с обеих сторон |
| Утечки мимо правил | Весь IPv4 и IPv6 трафик заходит в TUN; DNS на порт 53 перехватывается DNS-модулем Xray |
